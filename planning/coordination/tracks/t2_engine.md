- **E8c owner direction (2026-10-22, through the coordinator)**:
  1. Fallback accepted: a refused material draws with the built-in recipe, and every refusal is counted in the diagnostics.
  2. Image fills are **supported**, never refused, but no stock theme or default uses them; tests cover them. A face may be an image resampled to the target size with a deterministic, named filter (propose which and why). Intent: icons composited into a control face.
  3. CSS will need inline images: do not build it; write down in this file how a material's image layer maps to it, as a design question for the owner.
  4. Cost model: separate **bake cost** (paid once when a part's raster is rebuilt after an invalidation: state, size, scale, theme; then cached) from **live cost** (every composite: a blit of the cached raster, plus a group blend where one applies). A material's complexity affects only bake cost. Bound bake cost so an invalidation cannot stall. Replace the guessed per-layer constants with **measured bake times**; record workload and machine.
  5. Principle: the engine must not work around retained mode. Nothing in E5 to E8 may rasterize a material per frame. Report how E7 transitions bake today; if per frame, propose the retained form (baked endpoint rasters blended through a group, re-bake only at discrete state changes).
- **E7r (owner, 2026-10-22): a phase of its own, after E8c and before E9.** Today's per-frame bakes, all found in E7/E8b: animated parameters (the bulge `amplitude`), scale transitions (E8b), and expressions reading time_in_state or the pointer, plus ambient effects. Opacity and plain state changes are already retained. The retained forms:
  - (a) A state transition bakes each endpoint raster once and cross-fades them through a group (A at 1-t plus B at t, additive inside the group).
  - (b) Scale composites the cached raster through a transform during the motion, and re-bakes sharp at rest.
  - (c) Animated parameters (the bulge rise) bake a small fixed number of keyframes once (8 to 12; state the count and bound it) and step through them. No per-frame bake.
  - (d) Pointer and time inputs bake the static face once and composite a separately baked overlay. Ambient effects are a bounded loop of baked frames.
  - After E7r nothing in the engine bakes per frame. Prove it with a test or a counter: zero bakes while a transition runs between discrete changes.
- **E7r also includes slicing (owner, 2026-10-22).** It applies after E8c. E8c only has to keep the kernel able to render a reference box.
  - Slice cache: bake one reference part per (material, state, scale) and slice it into 4 corners, 4 edge strips and a centre. Any size is assembled from the slices by blit. Labels, icons and the focus ring are separate layers on top, so every button of a material shares one bake. The engine owns the shared cache and a theme change invalidates it; controls only borrow from it.
  - Sliceability per axis is declared by each material, or computed by the engine:
    - a gradient along an axis makes that axis non-sliceable, so key the cache on that dimension only (one bake per height, any width);
    - a radial gradient or an image fill makes the part non-sliceable, so use the whole-part cache;
    - below a per-material size threshold (blur and radius larger than half the size), use the whole-part cache;
    - count every fallback.
  - Device pixels: slices sit on device-pixel boundaries. Corners are baked at device scale and edges stretch exactly. State what happens at a fractional device position.
  - Cross-fade on slices: blend the slices, then assemble. This is linear, so it equals assembling then blending.
  - Area animations (the bulge keyframes) keep whole-part rasters.
  - Proof: counters for bakes, slice hits and whole-part fallbacks. A test: 20 buttons of different widths in one material and state give one bake. Pixel equality against the whole-part bake for sliceable materials.

- **CSS inline images (owner, 2026-10-22: by resource name, option A; not built yet).** An image is registered once as a resource (a decoded PNG) and a material layer names it. The mapping as written: A material's image layer (`MaterialFillLayer` of kind image: image id, pixel size, mode, slice, image scale, opacity) would map to CSS like this:
  - stretch: `background-image: <image>; background-size: 100% 100%; background-repeat: no-repeat`;
  - tile: `background-repeat: repeat; background-size: <w/scale>px <h/scale>px` (the image scale is source pixels per logical unit);
  - nine_patch: `border-image-source: <image>; border-image-slice: t r b l fill; border-image-width: <slice/scale>px; border-image-repeat: stretch`;
  - opacity: CSS has no per-layer background opacity. It needs an engine property (for example `-gf-image-opacity`) or `cross-fade()`;
  - the filter is the engine's single selected filter (see the open decision below). `image-rendering` could name it, but needs no value.
  - The open question is what `<image>` is: (A) a resource name, `url("resource:icon.check")`, resolved through the window's ImageRegistry, with bytes shipped in the theme package; or (B) an inline `data:image/png;base64,...` URI, decoded at theme load into the registry (PNG only, size-bounded). I recommend A, with B admitted only for small icons under a byte limit.
