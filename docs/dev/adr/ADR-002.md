# ADR-002: Implement the captured interface-level facade first; an unchanged-binary load is a late experiment, not a gate

Status: accepted (recorded retroactively)

Date: 2026-10-11 (decision in force since the compatibility programme began;
first written down on this date)

## Context

The source of the compatibility corpus (the retired compatibility specimen) is
not available. What is available is the shipped binary and its plugins, from
which a deterministic, non-executing capture produces the exact set of
Forms-shaped types and members the corpus calls. Two very different
compatibility strategies follow from that:

1. implement the captured interface-level facade, member by member, with
   GUI.Forms behaviour behind it and conformance traces that define that
   behaviour; or
2. aim first at loading the unchanged binary against a replacement framework
   under Wine and treat every observed difference as a requirement.

This decision was cited as ADR-002 by [`planning/MASTER_IMPLEMENTATION_PLAN.md`](https://github.com/malkuth-software/notes/blob/gui_forms/planning/MASTER_IMPLEMENTATION_PLAN.md)
before this file existed.

## Decision

Strategy 1 is the programme. The captured catalogue defines the required
surface; GUI.Forms traces define behaviour.

A later load of the unchanged binary under Wine is a **best-effort
compatibility experiment**. It is scheduled late, it is not a gate for any
earlier milestone, and its results are evidence of what the facade already
supports, not a source of new unbounded requirements. Reflection over the
capture supplies coverage; normative GUI.Forms traces supply behaviour.

## Consequences

- Coverage is reported as "identities resolved out of identities captured",
  a number the build can check. Behavioural support is reported separately
  per member, so presence is never mistaken for parity.
- The facade is generated from the capture and its behavioural rows are
  filled in against GUI.Forms traces; generated source is disposable and
  never becomes runtime truth.
- A difference observed when the unchanged binary runs is classified as a
  concrete blocker (fixed through a reviewed compatibility change), a
  documented deviation, or out of scope. It does not reopen the ordering
  decision in ADR-003.
- Reports about the unchanged-binary run are labelled compatibility evidence,
  never parity or redistribution.

## Rejected options

- **Unchanged-binary-first.** Rejected: without source, every runtime
  difference would be a guess at intent, the requirement set would be
  unbounded, and Wine itself would become part of the specification.
- **Skip the unchanged-binary run entirely.** Rejected: it remains the
  cheapest end-to-end check that the generated facade loads and behaves,
  provided it is scheduled after the surface exists.
