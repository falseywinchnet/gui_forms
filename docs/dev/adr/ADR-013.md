# ADR-013: Persistent side-panel composition is reserved to File Manager; demonstrations may compose panels

Status: retired 2026-10-13 by the owner (was accepted, recorded
retroactively; classification of demonstration programs added 2026-10-11)

Date: 2026-10-11 (topology rule in force since 2026-08-06; first written down
on this date)

## Context

GUI.Forms serves several planned applications: File Manager, Paint, a text
editor, games, and trusted host dialogs. File Manager's interface is built
around persistent left and right panels (navigation, details, previews) with
an embedded picker/browser that reuses the same topology. The other
applications each have one primary document, canvas or board surface.

Without a rule, every substantial application tends to acquire a dock/panel
host, and the toolkit tends to require one to deliver help, colour selection,
character selection, find/replace, rules, hints or settings. That makes
panels a dependency of the framework rather than a product decision of one
application.

This decision was cited as ADR-013 by `AGENTS.md` (hard boundaries),
[`planning/FUTURE_APPLICATION_CONSUMER_PROFILE.md`](https://github.com/malkuth-software/notes/blob/gui_forms/planning/FUTURE_APPLICATION_CONSUMER_PROFILE.md) (topology law) and the
polish-stage plan before this file existed.

## Decision

1. **Persistent side-panel composition is a File Manager product decision.**
   It is reserved to File Manager and to its embedded picker/browser. The
   fixture-backed `file_manager_demoboard/` consumer reproduces that interface
   and is the admitted first-party exception.
2. **Other consumers use owned dialogs.** Paint, the text editor, games and
   other ordinary applications obtain secondary tools through owned modal or
   modeless popup dialogs, or a bounded composited overlay. GUI.Forms must not
   require a dock/panel host for any of those tools.
3. **GUI.Forms may implement reusable panel controls.** `SplitContainer`,
   `MasterDetailView`, `CorrespondenceView`, `TreeView` and similar controls
   are ordinary library controls with the same tests as any other. The rule
   constrains consumer products, not the library's vocabulary.
4. **Demonstration programs are not consumer products.** The GUI.Forms
   Gallery and the Correspondence mail mockup may compose panels, including
   three-pane layouts, as demonstrations of the reusable panel controls.
   They exist to show what the controls do; they are not applications and do
   not acquire a product topology by being downloadable.
5. Plugins and providers never instantiate GUI.Forms objects or native
   windows, in any topology.

## Consequences

- Owned-dialog requirements (owner identity, modal scope, modeless owner
  tracking, focus return, per-monitor placement, nested-dialog limit, headless
  fixture support, no idle repaint) are first-class GUI.Forms capabilities,
  because every non-File-Manager application depends on them.
- A capability request that would make a panel host mandatory for a Paint,
  editor or game feature is routed back as an owned-dialog requirement.
- The demoboard's `AGENTS.md` governs its panel composition; it may not grow
  reusable controls or host capabilities inside the consumer directory.
- Future application capability routing is recorded in
  [`planning/FUTURE_APPLICATION_CONSUMER_PROFILE.md`](https://github.com/malkuth-software/notes/blob/gui_forms/planning/FUTURE_APPLICATION_CONSUMER_PROFILE.md); it does not alter the
  open implementation milestone by itself.

## Rejected options

- **A general dock/panel host as a framework service.** Rejected: it makes
  every application look like File Manager and couples unrelated features to
  panel availability.
- **Forbid panel controls in the library.** Rejected: File Manager needs
  them, and controls are tested library objects regardless of which product
  composes them.
- **Treat the mail mockup as a consumer product and refuse its layout.**
  Rejected on 2026-10-11: it demonstrates reusable controls and claims no
  product topology.

## Retirement, 2026-10-13

The owner retired this decision while settling the forward programme's
designer tools (the interface builder, the HTML layout designer and the
theme designer), which need a toolbox, a canvas and an inspector. The
reservation is dropped for every consumer: any application may compose
persistent panels from the reusable panel controls. Owned dialogs remain
first-class GUI.Forms capabilities, and plugins and providers still never
instantiate GUI.Forms objects or native windows.
