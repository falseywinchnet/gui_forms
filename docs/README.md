# GUI.Forms documentation (maintainer notes)

This directory is the source of the GUI.Forms documentation site. It follows
the layout and appearance of the NumPy documentation: Sphinx with the PyData
Sphinx Theme, sphinx-design overview cards, numpydoc-style reference pages and
the Sphinx C++ domain, published on Read the Docs and built in CI with
warnings treated as errors. These notes are for people editing the site; the
entry page is `index.rst`.

## Build locally

From the repository root:

```sh
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r docs/requirements.txt
python3 tools/generate_library_docs.py
sphinx-build -W -b html docs docs/_build/html
```

Open `docs/_build/html/index.html`. `docs/_build/` is ignored by Git. Always
build with `-W`: Read the Docs (`.readthedocs.yaml`, `fail_on_warning: true`)
and the `docs` job in `.github/workflows/native.yml` do. Add `--keep-going` to
see every warning in one run. `docs/requirements.txt` pins the versions the
site is checked with.

The version in the title is read from `project(GUIForms VERSION x.y.z)` in the
root `CMakeLists.txt` (`conf.py`, `read_project_version`).

## Layout

The top bar has NumPy's five sections. Each is a directory with an index page.

| Path | Section | Edited by |
|---|---|---|
| `index.rst` | Landing page: version, links, four overview cards | hand |
| `user/` | User guide: installation, first window, concepts, controls overview | hand |
| `api/` | API reference: controls by function, library by topic, one page per control and documented type | generated by `tools/generate_library_docs.py`; do not edit |
| `building/` | Building from source | hand |
| `dev/` | Development: contributing, decisions (`dev/adr/` includes `../../decisions/`), roadmap, evidence | hand |
| `release/` | Release notes; `0.1.md` includes `packaging/RELEASE_NOTES.md` | hand |
| `controls/generated/` | Alphabetical and by-function control indexes from `tools/control_registry.py render`; the control schema page from `tools/control_schema.py render` | generated; do not edit |
| `_static/` | `gui_forms.css` (adapted from NumPy's `numpy.css`), the logo mark and the card icons | hand |
| `library/` | API reference inputs: docstrings, `manual.json`, archived captures; see `library/README.md` | hand; excluded |
| `reference/` | Inputs of `tools/api_reference.py` (clang inventory, reviewed contracts) | generated or reviewed JSON; excluded |
| `notes/` | Dated internal working notes | kept for provenance; excluded |

## The exclude list

`conf.py` lists every path under `docs/` that is not a site page, explicitly,
because the build runs with `-W`: a page no toctree references is a warning.
When you add a page, add it to a toctree. When you add a non-page file, add
it to the exclude list with a comment saying why.

## Writing rules for site pages

- Present tense, addressed to a user of the library.
- No milestone numbers, no internal claim labels (the given/observed/measured
  vocabulary), no agent or role names.
- Link only to pages inside `docs/`. Refer to repository files outside `docs/`
  in backticks.
- ADR text is included, not copied. Edit `decisions/ADR-NNN-*.md`.
- Keep a hand-written page to roughly 150 lines; split rather than scroll.
- Control and type documentation belongs in `library/docstrings/`, not in a
  hand-written page; the generator turns it into the reference page.
- When a page moves or is renamed, add its old docname to `MOVED_PAGES` in
  `conf.py`. The build then writes a forwarding page at the old address, and
  fails if the old address is still a page or the new one is not.

## Page count and build time

The PyData theme renders only the current section's navigation into each
page, so the site can hold hundreds of pages. Keep generated pages to one per
documented type and one per category or topic; members are entries on their
type's page, never pages of their own. The full `-W` build takes about half a
minute.

## Generated inputs

Regenerate before building when headers, the registry or a docstring changed:

```sh
python3 tools/control_registry.py check          # validates manifests/controls.json
python3 tools/control_registry.py render         # writes controls/generated/
python3 tools/control_schema.py render           # writes controls/generated/schema.md
python3 tools/generate_library_docs.py           # writes api/ and tests/doc_examples_tests.cpp
```

The chevron bar at the top of the Roadmap page, `_static/roadmap.svg`, is drawn
by `python3 tools/make_roadmap_svg.py`. When a release changes, edit its `STAGES`
list and the matching section of `dev/roadmap.md` together, then commit the
regenerated image.

The `docs` CI job builds the site. The `house-style` job runs the registry
checks, the generator's unit tests and `generate_library_docs.py --check`; a
stale generated page fails the job rather than being rewritten silently. The
generated `tests/doc_examples_tests.cpp` builds and runs under `ctest`, so a
documented example that stops compiling or throws fails the native jobs.

## The clang declaration inventory is checked by maintainers, not CI

`tools/api_reference.py` keeps an exact declaration inventory,
`docs/reference/inventory.json`, extracted with `clang -ast-dump=json`, and
validates the reviewed contracts in `docs/reference/contracts/` against it.
The API reference pages use those contracts' remarks and member summaries.
`python3 tools/api_reference.py --check` compares the committed inventory byte
for byte with a fresh dump; the dump differs between compiler builds, so the
check runs locally with LLVM 22.1.8, not on CI runners.
