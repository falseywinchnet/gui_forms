# API reference inputs

This directory holds the hand-written inputs of the site's API reference.
The reference itself is MyST Markdown under `docs/api/`, generated by
`tools/generate_library_docs.py`; nothing here is a Sphinx page.

| Path | Role |
| --- | --- |
| `manual.json` | Hand-reviewed type summaries and method descriptions. Edited by people. |
| `captures/` | Control captures from the earlier atlas, kept as evidence. The reference does not publish them. |
| `MIGRATION_FRONTIER.md` | The per-type source isolation record from the earlier atlas. |

## Regenerate and check

```sh
python3 tools/generate_library_docs.py          # writes docs/api/
python3 tools/generate_library_docs.py --check  # fails if docs/api/ is stale
```

The generator reads every `class`, `struct` and `enum class` below
`include/gui_forms/` and the namespace-scope functions, constants and aliases
in those headers, skipping anything in a `detail` namespace or directory. It
groups stock controls by the function category in `manifests/controls.json`
and the rest of the library by header area, and writes one page per group.

A description comes from, in order: `manual.json`; the reviewed remarks and
member summaries in `docs/reference/contracts/*.json`; the `//` comment
directly above the declaration in the header. A member with none of these is
listed by its signature alone. The generator never writes a description from
a signature.

Private headers under `src/` are parsed too, only so that every narrative in
`manual.json` must still resolve to exactly one declaration. A narrative that
no longer resolves, or that names a method the type no longer declares, fails
both generation and `--check`.

## `manual.json` schema

```json
{
  "schema": 1,
  "types": {
    "TypeName": {
      "name": "TypeName",
      "declaration_header": "include/gui_forms/.../type_name.hpp",
      "summary": "One-paragraph description.",
      "method_scope": "public",
      "methods": {"method_name": "One sentence."}
    }
  }
}
```

`name` defaults to the key. `declaration_header` is required only when the
same type name is declared in more than one header. A method description
applies to every overload of that name. The older `status`, `visual`,
`capture` and `capture_note` fields are still accepted and ignored.
