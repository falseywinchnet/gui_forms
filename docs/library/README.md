# API reference inputs

This directory holds the hand-written inputs of the site's API reference. The
reference itself is reStructuredText under `docs/api/`, generated by
`tools/generate_library_docs.py`; nothing here is a Sphinx page.

| Path | Role |
| --- | --- |
| `docstrings/<TypeName>.rst` | One numpydoc-style docstring per documented type. A type with a docstring gets its own reference page. Edited by people. |
| `manual.json` | Older short type summaries and method descriptions, used where no docstring covers a member. |
| `captures/` | Control captures from the earlier atlas, kept as evidence. Not published. |
| `MIGRATION_FRONTIER.md` | The per-type source isolation record from the earlier atlas. |

## Regenerate and check

```sh
python3 tools/generate_library_docs.py          # writes docs/api/ and tests/doc_examples_tests.cpp
python3 tools/generate_library_docs.py --check  # fails if either is stale
```

Every stock control in `manifests/controls.json` and every type with a
docstring gets a page in the layout of a NumPy class page. Other public types
are documented on their category or topic page. The search box finds every
type and member.

A description comes from, in order: the type's docstring; `manual.json`; the
reviewed contracts in `docs/reference/contracts/*.json`; the `//` comment above
or after the declaration in its header. A member with none of these is listed
by its signature alone. Nothing is inferred from a signature.

## Writing a docstring

A docstring is a plain-text file in the layout of a
[numpydoc](https://numpydoc.readthedocs.io/en/latest/format.html) docstring.
`CheckBox.rst` is the model; copy its shape.

```rst
One-sentence summary in plain words: what the control is.

One or two short paragraphs: what it is for, how the user interacts with it,
and which control to use instead in the cases it is not for.

Parameters
----------
stable_id
    Constructor parameter, by its name in the header.

Properties
----------
checked : default ``false``
    A property is a getter, usually with a ``set_`` setter. Name it by the
    getter. The type comes from the header; write only ``default <value>``
    after the colon, and only when the header gives the default.

Events
------
checked_changed
    An ``Event<...>& name()`` accessor: when it is raised, what it carries,
    and in which order relative to other events.

Methods
-------
bind
    Any other public member function, by name. All overloads share the entry.

See Also
--------
RadioButton : One line on when to prefer it.

Notes
-----
Behaviour worth knowing: event order, input (mouse, keyboard, mnemonics,
focus), accessibility role, limits and errors.

Examples
--------
Introduce each example with a sentence.

.. code-block:: cpp

   ...
```

The generator checks every name in Parameters, Properties, Events and Methods
against the header and every See Also name against the public types; a name
that does not exist fails the build. Sections are optional but must appear in
this order. Members you do not describe are still listed with their exact
signatures.

Rules for the text:

- Describe what a user of the control sees and does, in present tense. Say
  "raised when the user clicks" rather than "publishes after commit".
- Every statement must match the header, the implementation under `src/` and
  the tests under `tests/`. Read them; do not paraphrase other summaries.
- Use single backticks for code: `` `checked` ``, `` `CheckState::checked` ``.
  Names of public types and of the type's own members become links.
- Observe events with `on(event, owner, &Owner::method)` on a `Component`
  owner. Never show `subscribe(...)`; it is deprecated.

Rules for examples:

- An example is either a function body, which the generator wraps in
  `void example()`, or declarations that include a `void example()`.
- Examples compile against `<gui_forms/gui_forms.hpp>` with
  `namespace gf = gui_forms;` and run without a native host, so they cannot
  call `Application::run`. Start a block with `// compile only` to compile it
  without running it.
- Follow the house style: spell every type (no `auto`), no lambdas, no `->`;
  write `(*pointer).member`.
- `tests/doc_examples_tests.cpp` is generated from these blocks and runs in
  CI, so an example that stops compiling or throws fails the build.

## `manual.json` schema

```json
{
  "schema": 1,
  "types": {
    "TypeName": {
      "name": "TypeName",
      "declaration_header": "include/gui_forms/.../type_name.hpp",
      "summary": "One-paragraph description.",
      "method_scope": "public",
      "methods": {"method_name": "One sentence."}
    }
  }
}
```

`name` defaults to the key. `declaration_header` is required only when the
same type name is declared in more than one header. The older `status`,
`visual`, `capture` and `capture_note` fields are accepted and ignored.
